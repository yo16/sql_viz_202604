## 1. 概要

日本語 / 英語の 2 言語を、クライアント状態のみで即時切替する。URL は変更せず、SEO用の
metadata は英語固定とし、SSR 初期出力の `<html lang>` も英語固定とする（要件 FI-6）。

設計の骨子:

1. 翻訳リソースは静的 TypeScript モジュールとしてアプリに同梱
2. 現在の言語は Zustand の独立ストア (`localeStore`) で保持
3. 初期化時に `localStorage` → `navigator.language` → `"ja"` の優先順で解決
4. `useLocale()` フックでリソース取得
5. `<html lang>` 属性は `<body>` 直後の**インラインスクリプト**で HTML パース時に同期的に確定させ、FOUC を防止
6. `<html>` タグには `suppressHydrationWarning` を付与し、SSR の `"ja"` とクライアント確定値の差異による hydration warning を抑制

## 2. 対応言語と型定義

```typescript
// src/i18n/types.ts
export type Locale = 'ja' | 'en';

export const SUPPORTED_LOCALES: readonly Locale[] = ['ja', 'en'] as const;

/**
 * SSR 時の初期 locale。
 * metadata 英語固定および SSR `<html lang="en">` と整合させるため "en"。
 * Zustand localeStore の初期値もこの値を使う。
 */
export const SSR_INITIAL_LOCALE: Locale = 'en';

/**
 * クライアント側で navigator.language が取得できないときのフォールバック (FI-2)。
 * 要件定義により "ja" で固定。SSR 初期値とは独立した概念。
 */
export const NAVIGATOR_UNAVAILABLE_FALLBACK: Locale = 'ja';

/**
 * 翻訳リソースで未定義キーが参照されたときのフォールバック (FI-4)。
 * 英語リソースを最終フォールバックとする。
 */
export const MESSAGE_FALLBACK_LOCALE: Locale = 'en';
```

**3種類のフォールバックの使い分け**:

| 定数 | 用途 | 値 | 根拠 |
|---|---|---|---|
| `SSR_INITIAL_LOCALE` | SSR レンダリング時の Zustand 初期値、`<html lang>` SSR 出力 | `"en"` | metadata 英語固定 (FI-6) との整合、SEO |
| `NAVIGATOR_UNAVAILABLE_FALLBACK` | クライアント側で `localStorage` 無・`navigator.language` 無のときの最終解決値 | `"ja"` | 要件 FI-2 |
| `MESSAGE_FALLBACK_LOCALE` | 翻訳キー欠落時のリソース参照先 | `"en"` | 要件 FI-4（ただし §6.3 の型制約で欠落はコンパイル時に検出されるため実質ランタイムでは発生しない） |

## 3. 初期言語の解決ロジック (FI-2, FI-3)

### 3.1 優先順位

1. `localStorage['sql-viz-locale']` が `"ja"` または `"en"` → その値 (FI-3)
2. `navigator.language` が `"ja"` で始まる → `"ja"`（それ以外 → `"en"`) (FI-2)
3. `navigator` 未取得時 → `NAVIGATOR_UNAVAILABLE_FALLBACK`（`"ja"`、FI-2）

注: SSR 時は `navigator` / `localStorage` が存在しないが、これは「navigator 未取得」ケース
ではなく**サーバー環境**である。SSR 時の Zustand ストア初期値および `<html lang>` は上記
優先順位とは独立に `SSR_INITIAL_LOCALE`（`"en"`）を用いる（§8.1 参照）。クライアントに
到達後、インラインスクリプトと `resolveInitialLocale()` が上記優先順位でそれぞれ DOM と
ストアを更新する。

### 3.2 React 側の実装（ストア初期値用）

```typescript
// src/i18n/resolveInitialLocale.ts
export function resolveInitialLocale(): Locale {
  // 1. localStorage を最優先 (FI-3)
  const saved = readSavedLocale();
  if (saved) return saved;

  // 2. navigator.language による自動判定 (FI-2)
  if (typeof navigator !== 'undefined' && navigator.language) {
    return navigator.language.toLowerCase().startsWith('ja') ? 'ja' : 'en';
  }

  // 3. navigator.language が取得できない → 日本語 (FI-2 フォールバック)
  return NAVIGATOR_UNAVAILABLE_FALLBACK;
}
```

### 3.3 二重実装の設計意図（重要）

同じ優先順位ロジックを **インラインスクリプト（DOM 用）** と
**`resolveInitialLocale()`（Zustand ストア用）** で**独立に2回実装**する。
これは避けられない冗長性である。

| 実行箇所 | 目的 | 実行タイミング | 書き込み先 |
|---|---|---|---|
| `<body>` 直後のインラインスクリプト | FOUC 防止 | HTML パース中（同期） | `document.documentElement.lang` |
| `LocaleBootstrap` 内の React コード | ストア初期値反映 | hydration 後 (`useEffect`) | Zustand `localeStore.locale` |

**なぜ二重になるか**:
- インラインスクリプトは React のレンダリング前に走るため、Zustand ストアにアクセスできない
- React 側 (`LocaleBootstrap`) は hydration 後にしか走らないため、DOM の `<html lang>` を SSR 時点で正しくできない
- 両者は別ソースを書き換えるが、**同じ優先順位ロジックを実装しなければ整合性が崩れる**

**整合性担保**:
- 両実装の優先順位は本節 3.1 を正として、PR レビュー時に必ず突き合わせる
- 片方を変更したら必ずもう片方を更新する
- テストで両者が同じ入力に対し同じ結果を返すことを確認する（§11 参照）

### 3.4 SSR 注意点

Next.js の SSR 時には `navigator` / `localStorage` が存在しない。SSR レンダリング結果の
`<html lang>` は常に `"en"` で出力される（metadata 英語固定と整合させるため）。
クライアント到達後、`<body>` 直後のインラインスクリプトが HTML パース中に `<html lang>` を
確定（ユーザーの選択が `"ja"` の場合のみ `"ja"` に書き換え）し、その後 React の hydration が走る。

## 4. 永続化 (FI-3)

| 項目 | 値 |
|---|---|
| ストレージ | `localStorage` |
| キー | `"sql-viz-locale"` |
| 値 | `"ja"` または `"en"`（それ以外の値は無視して自動判定にフォールバック） |

```typescript
// src/i18n/persistence.ts
const STORAGE_KEY = 'sql-viz-locale';

export function readSavedLocale(): Locale | null {
  try {
    const v = localStorage.getItem(STORAGE_KEY);
    return v === 'ja' || v === 'en' ? v : null;
  } catch {
    return null;  // プライベートモード等で localStorage が使えないケース
  }
}

export function writeSavedLocale(locale: Locale): void {
  try {
    localStorage.setItem(STORAGE_KEY, locale);
  } catch {
    // 保存失敗は致命的でないため握りつぶす
  }
}
```

## 5. 状態管理 — localeStore

`lineageStore` / `flowStore` とは独立した第3のストアとして実装する。
リネージュの再計算を言語切替でトリガーしないためにストアを分離する。

```typescript
// src/stores/localeStore.ts
interface LocaleStore {
  locale: Locale;                // 初期値は SSR_INITIAL_LOCALE ("en")
  setLocale: (locale: Locale) => void;       // ストア + localStorage + <html lang> を同時更新（ユーザー操作用）
  _initializeLocale: (locale: Locale) => void; // hydration 直後の初期反映のみ（DOM は触らない）
}
```

**重要**: ストアの初期値は `SSR_INITIAL_LOCALE`（`"en"`）。これは SSR レンダリング時の
`<html lang="en">` と整合させ、Googlebot が索引化する初期 HTML スナップショットで
コンポーネント内の英語 metadata とテキストが一貫するようにするため。日本語ユーザーに
対しては hydration 後に `LocaleBootstrap` → `_initializeLocale("ja")` でストアが切り替わる。

**更新の副作用**:
1. ストアの `locale` 更新
2. `writeSavedLocale(locale)` で `localStorage` 保存
3. `document.documentElement.setAttribute('lang', locale)` で `<html lang>` 更新

これらは `setLocale` 内でまとめて行う。`<html lang>` の初期値確定はインラインスクリプトが
担当し（§8 参照）、`setLocale` はユーザー操作による切替時の `<html lang>` 更新のみを担う。

### 5.1 Zustand `persist` ミドルウェアを使わない理由

本プロジェクトの `lineageStore` / `flowStore` と同様、`localeStore` も自前で
`localStorage` を読み書きする（`persist` ミドルウェアは使用しない）。

理由:
- **SSR hydration ミスマッチの既知問題**: `persist` はクライアントでの rehydrate 時に
  ストア値を書き換えるが、これが React の hydration タイミングと噛み合わず、
  初回描画と rehydrate 後描画の差分による警告やちらつきを発生させやすい
- **`_hasHydrated` フラグ運用の煩雑さ**: `persist` を安全に使うには rehydrate 完了を
  フラグで待つ実装が必要で、UI コードが複雑化する
- **プロジェクト内一貫性**: lineageStore / flowStore と同じパターンを採用することで、
  ストア実装の学習コストを下げる
- **本 FOUC 設計との適合性**: 本設計ではインラインスクリプトが DOM を先に確定させるため、
  ストアへの初期値書き込みタイミングはレンダリングのちらつきに影響しない。`persist` の
  rehydrate タイミング問題を回避できる。

## 7. 使用API — useLocale フック

```typescript
// src/i18n/useLocale.ts
export function useLocale() {
  const locale = useLocaleStore((s) => s.locale);
  const setLocale = useLocaleStore((s) => s.setLocale);
  const messages = locale === 'ja' ? ja : en;
  return { locale, setLocale, t: messages };
}
```

使用例:

```typescript
const { t, locale, setLocale } = useLocale();
return <h1>{t.header.title}</h1>;
```

**方針**: フラットな関数 `t('key.path')` ではなくオブジェクトアクセス (`t.header.title`) を
採用する理由:
- TypeScript の型推論でキー誤りをコンパイル時に検出可能
- 補完が効く
- パラメータ埋め込みが必要な箇所のみ `formatMessage(t.error.apiRequestFailed, { ... })`
  のようなヘルパを併用

## 8. `<html lang>` 属性の切替 (FI-1)

### 8.1 方針サマリ

SSR 時は `<html lang="en">` 固定で出力する（metadata 英語固定と整合）。クライアントでは
以下の3段階で `<html lang>` を確定・更新する:

| タイミング | 担当 | 目的 |
|---|---|---|
| HTML パース時（同期） | `<body>` 直後のインラインスクリプト | 初期値確定（FOUC 防止） |
| React hydration 後 | `LocaleBootstrap` の `useEffect` | Zustand ストアに初期値を書き込む（DOM は触らない） |
| ユーザー言語切替時 | `localeStore.setLocale` | ストア更新 + `localStorage` 保存 + `<html lang>` 更新 |

### 8.2 `<html>` タグへの `suppressHydrationWarning`

`app/layout.tsx` の `<html>` に `suppressHydrationWarning` を付与する。

```tsx
<html lang="en" suppressHydrationWarning>
```

理由:
- SSR は `<html lang="en">` 固定だが、ユーザーが日本語を選択している場合
  （前回 `"ja"` を選択、または `navigator.language` が `ja*` の場合）、
  インラインスクリプトが hydration 前に `lang="ja"` に書き換える
- hydration 時点で SSR マークアップとクライアント DOM が異なるため、
  React は hydration warning を出す
- `<html>` タグ自体に `suppressHydrationWarning` を付けることでこの警告のみ抑制する
  （他要素の hydration 警告は通常通り発生する）

### 8.3 FOUC 防止インラインスクリプト

`app/layout.tsx` の `<body>` 直後（既存の JSON-LD 用 `<script dangerouslySetInnerHTML>` と
同じパターン）に、以下のインラインスクリプトを配置する。

```tsx
<body>
  <script
    dangerouslySetInnerHTML={{
      __html: `
(function() {
  try {
    var saved = localStorage.getItem('sql-viz-locale');
    var locale = (saved === 'ja' || saved === 'en') ? saved
      : (navigator.language && navigator.language.toLowerCase().startsWith('ja') ? 'ja'
        : (navigator.language ? 'en' : 'ja'));
    if (locale === 'ja') {
      document.documentElement.setAttribute('lang', 'ja');
    }
  } catch(e) {}
})();
      `.trim(),
    }}
  />
  {/* 既存の JSON-LD スクリプト、children 等が続く */}
</body>
```

ポイント:
- **HTML パース中に同期実行**されるため、最初の paint 時点で `<html lang>` は確定済み
- 初期値が `"en"` の場合は DOM 書き換え不要（SSR 出力のまま）。`"ja"` の場合のみ `setAttribute('lang', 'ja')`
- `try-catch` で `localStorage` 例外を握りつぶす（プライベートモード等）
- React のレンダリングより前に走るため、ストアには触れない
- 優先順位ロジックは §3.1 の仕様に合わせる（`resolveInitialLocale()` と**同一ロジック**）。`navigator` 未取得時は `'ja'` にフォールバック

### 8.4 `LocaleBootstrap` の責務

`LocaleBootstrap` は hydration 後に**ストアの初期値だけ**を設定する。
DOM の `<html lang>` には**触らない**（インラインスクリプトが既に確定済みのため）。

```typescript
// src/i18n/LocaleBootstrap.tsx
"use client";

export function LocaleBootstrap() {
  useEffect(() => {
    // resolveInitialLocale() はインラインスクリプトと同じ優先順位で解決する
    const initial = resolveInitialLocale();
    useLocaleStore.getState()._initializeLocale(initial);
  }, []);
  return null;
}
```

`_initializeLocale` は DOM を触らず localStorage にも書き込まないバリアント（ストアの
`locale` を更新するのみ）。これによりインラインスクリプトが確定した `<html lang>` を
後から React が上書きしないことと、初期化時に localStorage を無意味に上書きしないことを保証する。

### 8.5 ユーザー切替時

LanguageSelector クリック → `setLocale(next)` → 3つの副作用（ストア、localStorage、
`<html lang>`）を同時実行。このケースでは既にクライアントランタイムなので
インラインスクリプトは関係ない。

## 10. metadata / SEO 方針 (FI-6)

- `app/layout.tsx` の `metadata` export は**英語固定**とする
- `openGraph.locale` は `"en_US"` 固定
- `<title>` / `description` / `keywords` / JSON-LD はすべて英語文言で記述する
- SSR 初期出力の `<html lang>` も `"en"` 固定とし、metadata との整合性を保つ
- 日本語選択時も metadata は英語のまま（クライアント言語切替は画面内テキストと
  `<html lang>` 属性のみを切り替え、metadata には影響しない）

### 10.1 英語固定の技術的根拠

- **検索エンジンはクライアントサイドの `<html lang>` 変更を索引化しない**:
  Google は SSR/初期 HTML の言語タグとメタ情報を基準に索引化する。クライアント JavaScript
  による `<html lang>` 書き換えは Googlebot がレンダリングしたとしても言語別のインデックスには
  寄与しにくい。単一URL・単一 metadata の構成とする
- **英語市場を SEO の主要ターゲットとする**: 想定ユーザーは DWH 開発者であり、技術系の
  検索クエリは英語が優勢。metadata を英語にすることで検索流入の最大化を図る
- **`<html lang>` と metadata の整合性**: SSR 初期出力を `<html lang="en">` + 英語 metadata
  に揃えることで、Googlebot の初期 HTML スナップショットが一貫した英語ページとして認識される
- **日本語ユーザーへの影響**: 日本語ユーザーは HTML 到達後にインラインスクリプトが
  `<html lang="ja">` に書き換え、画面内テキストも日本語で表示される。ブラウザタブのタイトル
  は英語のままだが、これは許容範囲（URL分割を避ける代償）
- **将来の拡張**: 日本語 SEO も強化したい場合は URL 分割 (`/ja/*`, `/en/*`) + Next.js
  `Metadata` `alternates.languages` を用いて SSR レベルで言語別 metadata を出力する構成に
  切り替える（本設計のスコープ外）

## 13. ライブラリ選定の記録

### 13.1 採用しないライブラリと理由

**next-intl、next-i18next、react-i18next はいずれも採用しない**。自前の Zustand ベース実装を選択する。

| ライブラリ | 不採用理由 |
|---|---|
| **next-intl** | サーバーコンポーネントでの `useTranslations` や `next-intl/middleware` が前提としている URL 分割（`/ja/*`, `/en/*`）を本設計では使わない（要件 FI-6 により URL不変）。URL不変の構成で使う場合、`NextIntlClientProvider` の初期化時にサーバーで locale を決める必要があり、クライアント状態のみで切り替える本設計と相性が悪い |
| **next-i18next** | Pages Router 前提の設計が強く、App Router では公式にサポートされていない |
| **react-i18next** | 2言語・約24キーの規模では機能過剰。バンドルサイズも不要に増える。型安全なキー補完は自作の `Messages` 型で十分担保できる |

### 13.2 自前実装を選ぶ理由

1. **URL分割を使わない**: 要件 FI-6 により単一URL（日本語コンテンツをメインとする metadata 固定）
2. **小規模辞書**: 2言語・約24キー（§6.4）。i18n ライブラリの辞書読込機構は過剰
3. **TypeScript で十分**: `ja.ts` を正とし `Messages = typeof ja` 型を導出、`en: Messages`
   の制約でキー欠落を `tsc` がコンパイル時に検出できる（§6.3）
4. **プロジェクト内一貫性**: 既存の `lineageStore` / `flowStore` と同じ「自前 Zustand +
   自前 localStorage」パターンに揃える。`persist` ミドルウェアも使わない（§5.1）
5. **フレームワーク非依存性**: 将来 React Flow 以外のビューエンジンに切り替える場合も、
   i18n 層は影響を受けない

### 13.3 将来のライブラリ導入を検討するトリガー

- 言語数が 3 以上に増える
- 辞書キーが 100 を超える
- 複数形・日付・数値フォーマットなど ICU MessageFormat が必要になる
- 英語SEO対応（`/en/*` ルート分割）を行う → このタイミングで `next-intl` 導入を再検討

## 14. SSR / hydration 戦略のまとめ

本設計における SSR / hydration の全体像を一枚にまとめる。

### 14.1 3 つの構成要素の役割

| 要素 | 配置 | 実行タイミング | 責務 | 触る対象 |
|---|---|---|---|---|
| `<html lang="en" suppressHydrationWarning>` | `app/layout.tsx` の `<html>` タグ | SSR 出力＋hydration 時 | 初期 lang を英語で出力（metadata と整合）、インラインスクリプトによる書換で発生する hydration warning を抑制 | （属性のみ） |
| インラインスクリプト | `<body>` 直後 `<script dangerouslySetInnerHTML>` | HTML パース中（同期、React 前） | `<html lang>` を `localStorage`/`navigator` から確定（FOUC 防止） | `document.documentElement.lang` |
| `LocaleBootstrap` | `app/layout.tsx` の children 先頭 | React hydration 後 `useEffect` | Zustand `localeStore` の初期値を確定 | `useLocaleStore` |

### 14.2 タイムライン

```
[SSR]
  └─ <html lang="en" suppressHydrationWarning> + 英語 metadata
     + <body>{inline script}{children}</body> を出力

[クライアント HTML パース]
  └─ <body> 直後のインラインスクリプトが同期実行
       → localStorage/navigator から locale を決定
       → "ja" なら <html lang="ja"> に書換（"en" なら何もしない）

[初期 paint]
  └─ <html lang> は既に正しい値。React コンポーネントは localeStore の SSR 初期値
     (SSR_INITIAL_LOCALE = "en") の文言で描画される
  ※ ここでの「FOUC 防止」とはあくまで <html lang> 属性のちらつき防止。
     本文テキスト自体の一瞬の切替は LocaleBootstrap 後に発生しうる

[React hydration]
  └─ <html> タグの lang 属性差分は suppressHydrationWarning で警告抑制
  └─ LocaleBootstrap の useEffect が走り、resolveInitialLocale() で locale を解決
     → localeStore._initializeLocale(locale) を呼ぶ（DOM は触らない）
     → ストア更新により購読コンポーネントが正しい言語で再レンダリング

[ユーザー言語切替]
  └─ LanguageSelector クリック → setLocale(next)
     → ストア更新 + localStorage 保存 + <html lang> 更新を同時実行
```

### 14.3 トレードオフと容認する点

- **本文テキストの初期ちらつき**: インラインスクリプトは `<html lang>` のみを書き換える。
  React コンポーネントが表示する本文テキストは `LocaleBootstrap` の `useEffect` 実行後に
  英語へ切り替わるため、初回描画から hydration 完了までの短時間は日本語文言が見える
  可能性がある。これを完全に防ぐには URL 分割 SSR が必要であり、本設計スコープ外
- **インラインスクリプトと `resolveInitialLocale()` の重複**: §3.3 で記述したとおり
  避けられない冗長性。テストで両者の等価性を担保する
- **`suppressHydrationWarning` の副作用**: `<html>` タグの子孫要素の hydration warning は
  通常通り発生する。`<html>` タグ直下の属性差分のみが抑制対象
